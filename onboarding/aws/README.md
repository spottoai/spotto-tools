# AWS onboarding scripts

Configure Spotto access in any company's AWS accounts with Bash or PowerShell and
AWS CLI v2. Both scripts use the exact trust, discovery, guardrail, billing and
optional commitments policies generated by Spotto for your company. It supports
standalone accounts and manually configured AWS organizations, including separate
accounts for billing definitions and S3 storage.

Choose `setup-spotto-aws.sh` for Bash or `Setup-SpottoAws.ps1` for PowerShell.
Each is a standalone script. Download your chosen script alongside your company
setup package; no companion module or Terraform installation is needed.

- Bash: Bash 3.2+, AWS CLI v2, jq 1.6+, and GNU `timeout`. Linux and AWS CloudShell
  normally provide `timeout` through coreutils. On macOS, run `brew install jq coreutils`
  to provide jq and `gtimeout`; install AWS CLI v2 separately.
- PowerShell: PowerShell 7.4+ and AWS CLI v2.

To manage the role with Terraform instead, use
[terraform-aws-spotto](https://github.com/spottoai/terraform-aws-spotto). It consumes
the same setup package and produces the same results JSON.

## Prepare the setup package

1. In Spotto, open **Connectors → Cloud Accounts**, select **Create**, then **AWS**,
   and choose **Add Account** or **Add Organization**.
2. Add the AWS account or organization and its intended account list. Each enabled
   account uses `SpottoReadOnlyRole`. Advanced custom role paths use the existing
   manual onboarding flow.
3. Billing is optional. To reuse a Data Export or CUR, enter its exact definition,
   export name, S3 destination, Region and optional KMS key. The definition role
   account and storage role account may differ. Use **Discover Exports** and
   **Validate Export Destination** on the **Billing** step if needed. Those actions
   require an initial role. For either script, first leave billing sources
   empty, download a discovery-only package, and run the wizard in configure mode.
   Then add billing sources. If role-based discovery needs definition access,
   choose **Manual IAM** on the **Deploy Access** step, generate that account's role
   instructions with **Generate Role Instructions**, and apply the generated
   bootstrap **SpottoBillingExportRead** inline policy to the existing role in IAM.
   After choosing exports, regenerate and apply the exact definition policy before
   **Validate Export Destination**. Once destinations are complete, download a new
   package and rerun the wizard to apply exact export/storage access. You can also
   enter the export coordinates directly from AWS Billing using your administrator
   session. If you choose CloudFormation for the initial role instead, finish that
   account by updating its owning stack; these scripts only verify
   roles from the Spotto CloudFormation template.
4. On the **Deploy Access** step, choose **Bash, PowerShell or Terraform**, then **Download
   Setup Package**. Review the trust and permission policies in `spotto-aws-setup.json`.
   The package contains the server-issued company External ID; do not invent or
   replace it. This is setup after company registration, not AWS account creation.

The wizard supports up to 100 enabled accounts and a 1 MiB package. It does not
create new billing exports, storage buckets, AWS accounts, or security services.
An empty billing base prefix is supported for exports delivered at the bucket
root; access remains scoped to the export's delivery directory.

## Run locally with Bash

Sign in with AWS CLI using your normal AWS IAM Identity Center/SSO profile or
another authorized session. Do not give Spotto administrator credentials.

Complete authentication in your terminal before running Bash. For an assume-role
profile with MFA, run `aws sts get-caller-identity --profile customer-admin` once
and enter the MFA code; AWS CLI caches that role session. For IAM Identity Center,
run `aws sso login --profile customer-admin`, then check the identity with the same
profile. Credential helpers must also supply a cached, noninteractive session.
Repeat for each profile in a multi-account map. CloudShell can use its current
authorized session without a profile.

The Bash script runs supervised CLI jobs in their own process groups so deadlines
and cancellation also stop their children. These jobs cannot complete terminal
login prompts. An identity-check timeout prints the preauthentication commands;
finish login in your terminal and rerun. The script probes jq features and GNU
timeout support before reading the package, with dependency-specific errors.

```bash
git clone https://github.com/spottoai/spotto-tools.git
cd spotto-tools
bash ./onboarding/aws/setup-spotto-aws.sh \
  --setup-package ./spotto-aws-setup.json \
  --profile customer-admin
```

Press Enter to check configuration without changing AWS, or choose configure mode
to review and approve the exact IAM changes. You can also select a mode explicitly:

```bash
# Read-only comparison (also the default in non-interactive mode).
bash ./onboarding/aws/setup-spotto-aws.sh \
  --setup-package ./spotto-aws-setup.json --profile customer-admin --check-only

# Preview the changes without applying them.
bash ./onboarding/aws/setup-spotto-aws.sh \
  --setup-package ./spotto-aws-setup.json --profile customer-admin --dry-run

# Configure after reviewing and approving the displayed changes.
bash ./onboarding/aws/setup-spotto-aws.sh \
  --setup-package ./spotto-aws-setup.json --profile customer-admin --configure
```

Use `--help` for all options. Bash is required; do not run the script with `sh`.
The script checks each AWS identity before any account is changed and rechecks
the account and approved role state immediately before applying changes.

## Run locally with PowerShell

Sign in with AWS CLI using your normal AWS IAM Identity Center/SSO profile or
another authorized customer session. Do not give Spotto administrator credentials.

```powershell
git clone https://github.com/spottoai/spotto-tools.git
Set-Location ./spotto-tools
pwsh -NoProfile -File ./onboarding/aws/Setup-SpottoAws.ps1 `
    -SetupPackagePath ./spotto-aws-setup.json `
    -Profile customer-admin
```

The interactive wizard defaults to checking prerequisites/configuration. Select
configure mode to review and approve role changes. Each account's signed-in AWS
identity is checked before any account is modified. The customer operator needs
the IAM reads listed below and provisioning permissions for setup.

## Run in AWS CloudShell

CloudShell defaults to Bash. Upload your setup package, then download and run the
Bash script with the current authorized AWS session:

```bash
curl --fail --show-error --location \
  https://raw.githubusercontent.com/spottoai/spotto-tools/main/onboarding/aws/setup-spotto-aws.sh \
  --output ./setup-spotto-aws.sh

bash ./setup-spotto-aws.sh --setup-package ./spotto-aws-setup.json
```

To use PowerShell instead, enter `pwsh`, then run:

```powershell
Invoke-WebRequest `
    -Uri "https://raw.githubusercontent.com/spottoai/spotto-tools/main/onboarding/aws/Setup-SpottoAws.ps1" `
    -OutFile "./Setup-SpottoAws.ps1"

pwsh -NoProfile -File ./Setup-SpottoAws.ps1 `
    -SetupPackagePath ./spotto-aws-setup.json
```

The current CloudShell session supplies credentials. For multiple accounts, use
authorized per-account CLI profiles. Access to an organization management account
does not automatically grant IAM administration in its member accounts.

## Multiple profiles and unattended use

Create a profile map containing names only, preserving AWS account IDs as strings:

```json
{
  "111122223333": "customer-management-admin",
  "000011112222": "customer-storage-admin"
}
```

```powershell
pwsh -NoProfile -File ./onboarding/aws/Setup-SpottoAws.ps1 `
    -SetupPackagePath ./spotto-aws-setup.json `
    -ProfileMapPath ./profiles.json `
    -CheckOnly -NonInteractive
```

For Bash, use the same profile map:

```bash
bash ./onboarding/aws/setup-spotto-aws.sh \
  --setup-package ./spotto-aws-setup.json \
  --profile-map ./profiles.json --check-only --non-interactive

# Deliberately approve unattended configuration after reviewing the package.
bash ./onboarding/aws/setup-spotto-aws.sh \
  --setup-package ./spotto-aws-setup.json \
  --profile-map ./profiles.json --configure --non-interactive --yes
```

`--profile` supplies a fallback for accounts absent from the map. An explicitly
mapped empty profile name uses the current AWS session. Every resolved identity
must match its target account. Bash supports `--region` (default `us-east-1`),
`--output` for a new results path, and `--repair-existing-role` for explicit
adoption. `--configure`, `--check-only`, and `--dry-run` are mutually exclusive.
Unattended configure mode requires `--yes`; it never assumes approval from EOF.

Use `-WhatIf` to read existing IAM configuration and preview changes without
modifying AWS. `-NonInteractive` requires the package path and enough profile
mappings and defaults to check-only. To deliberately approve unattended configuration, use configure mode
with `-NonInteractive -Confirm:$false` after reviewing the package. Neither
check-only nor WhatIf proves operator write access; write permissions are exercised
only during approved setup. All AWS CLI calls have timeouts; IAM propagation errors
are retried at most four times with bounded backoff.
The Bash equivalents are `--dry-run`, `--non-interactive`, and
`--configure --non-interactive --yes`. Its AWS calls have a 45-second deadline
with a further two seconds before forced termination. It enables AWS CLI standard
retries with at most three total attempts inside each deadline, and separately
retries IAM propagation (`NoSuchEntity`) errors for policy writes with bounded backoff.
If the Bash script receives Ctrl+C or SIGTERM, it stops the active account workflow
and terminates its AWS CLI process group before exiting. A request already accepted
by AWS may still have completed. Inspect the role and rerun with the same package;
unchanged configuration is not rewritten. Cancellation does not produce a completed
results file.

## Existing roles and reruns

New roles are tagged `SpottoCompanyId` and `SpottoManagedBy=Setup-SpottoAws`.
Both scripts share this ownership tag, so either can maintain a role created by
the other. Run one writer at a time for each role.
IAM role tag keys are compared without case sensitivity. Tag values retain their
exact case. An existing `SpottoManagedBy` tag with an empty value is also verify-only.
For each account, check-only mode and the approval prompt list the exact IAM changes:
inline policies to add, replace or delete, trust policy replacement (including how
many existing trust statements it removes), ownership tags and managed policies to
attach. Only those differences are written, so an unchanged rerun performs no IAM
writes and a rerun after a partial failure applies only what is still missing.
Only `SpottoGuardrails`, `SpottoBillingExportRead`, and `SpottoCommitmentsPlanning`
are managed. Deselected billing/commitments policies with those exact names are
removed after approval. Other customer policies are preserved, so review them
separately if you require the role to have only Spotto permissions.

An existing role that already matches the generated configuration, for example one
created from the manual instructions, is reported as `configured` (or
`configuration-matches` in check-only mode) without any writes or adoption. To change
an existing customer-managed role, rerun with `-RepairExistingRole` and approve the
listed changes; this also adds the ownership tags. The role is never deleted or
recreated. The script refuses roles tagged for another company and roles whose trust
uses another External ID. Roles created from the Spotto CloudFormation template are
tagged `SpottoManagedBy=CloudFormation` and are verify-only (see below); update their
stack with a new portal template instead. If Terraform, CDK,
StackSets or Control Tower customizations manage the role, apply the generated
policies there instead; the next deployment would otherwise revert the wizard.

A role tagged `SpottoManagedBy` with any value other than `Setup-SpottoAws`, such as
`Terraform` from [terraform-aws-spotto](https://github.com/spottoai/terraform-aws-spotto)
or `CloudFormation` from the Spotto portal template, is verify-only:
- If it matches the package, check-only reports `configuration-matches` and
  configure mode reports `configured`, with no writes.
- If it differs, the wizard lists the changes and refuses to make them, even with
  `-RepairExistingRole`. Apply them with the owning tool.

CloudFormation stack tags (`aws:cloudformation:*`) establish verify-only ownership
even if an old script ownership tag is also present. Matching roles can be checked
without writes; any drift must be repaired through the owning stack.

If the role has a permissions boundary, the wizard warns and names it. Boundaries are
never changed, but they can deny Spotto reads even when the role policies match.

After approval, the wizard rechecks the AWS account, immutable role ID, ownership
tags, trust and the approved change list before issuing changes. A replaced, removed,
newly created, reassigned or otherwise changed role requires a new review. Run one writer at a time for each role:
IAM has no conditional role updates, so concurrent changes during the mutation
sequence cannot be made atomic by this script.

The wizard installs guardrails before broad managed policies and before changing
an existing role's trust. A failed run may leave partially configured permissions;
the account is reported as failed and a rerun can repair it. AWS role configuration
requires these operator permissions as applicable:

- `sts:GetCallerIdentity`
- `iam:GetRole`, `iam:ListAttachedRolePolicies`, `iam:ListRolePolicies`, `iam:GetRolePolicy`
- `iam:CreateRole`, `iam:TagRole`, `iam:UpdateAssumeRolePolicy`, `iam:PutRolePolicy`,
  `iam:DeleteRolePolicy`, `iam:AttachRolePolicy`

Current generated packages carry the discovery action allowlist and guardrails in
`SpottoGuardrails` and need no AWS-managed policy attachments. Older generated
packages may request `SecurityAudit` and `ReadOnlyAccess`; the scripts apply only
the attachments in the package. They do not detach unrelated or legacy attachments.
Review and remove obsolete attachments with the owning tool after validating the
replacement. Optional commitments planning includes starting a Savings Plans
recommendation calculation; it does not purchase commitments. Select capabilities
in the portal before generating the package.

In check-only, configure and dry-run/WhatIf modes, both scripts warn if either
legacy attachment remains but is not requested by the package. They name the ARNs,
preserve the attachments, and leave the configuration-match result unchanged.
Validate replacement access in Spotto before removing legacy attachments with the
owning tool. Terraform removes the legacy attachments it tracks in state when a
current package no longer requests them; unmanaged attachments remain unchanged.

## Finish in Spotto

The wizard writes a new `SpottoAwsOnboarding-<timestamp>-<suffix>.json` file without
overwriting existing files. `-OutputPath` selects another new path. The handoff
contains company/account configuration and outcomes, but no credentials or External
ID. Paste its full contents into **Setup Results JSON**, then select **Read Setup
Results**. It must match the current company and unchanged configuration.
The portal displays results without changing or saving the draft.

For Bash, use `--output` instead of PowerShell's `-OutputPath`. Both scripts write
owner-only results files on Linux/macOS and refuse to overwrite an existing path.

Select **Create** or **Update** to let Spotto validate the configured trusted principal,
resource reads, export definitions, S3/KMS object access and start onboarding.
`configured` means IAM setup completed; it does not mean Spotto can access every
service. `configuration-matches` is a read-only comparison. `changes-required`,
`planned`, and `failed` need action before relying on the setup. Failed account
setup returns exit code 1 and still writes results for all attempted accounts.
Wrong-account profile resolution stops before any AWS change and writes no result.

SCPs and permissions boundaries can deny access even with correct role policies.
S3 bucket policies and KMS key policies can also require customer administrator
changes. The wizard reports failures and leaves those governance controls to the
customer. Billing exports without delivered files remain pending in Spotto.

## Offline verification

On Linux/macOS with Python 3 and PowerShell 7.4+:

```powershell
pwsh -NoProfile -File ./onboarding/aws/tests/Setup-SpottoAws.Offline.ps1
```

Tests run the real entrypoint against isolated fake AWS CLI processes and never
contact AWS. Operator permissions and effective Spotto access require a
customer-authorized live onboarding run.

For Bash, with Python 3.9+ and the Bash script prerequisites:

```bash
python3 -m unittest discover -s onboarding/aws/tests -p 'test_*.py' -v
bash -n onboarding/aws/setup-spotto-aws.sh
```

The suite runs a standalone copy from a directory with spaces. It covers read-only
defaults, approval, account identity checks, safe repair and reruns, ownership,
partial failures, propagation retries, timeout handling, result permissions and
the portal JSON contract, and cancellation of account/CLI processes.
`tests/fixtures/spotto-aws-setup.json` is copied unchanged
from `terraform-aws-spotto/tests/fixtures/spotto-aws-setup.json`, which is generated
by the real API bundle builder. Regenerate it there and copy it here when the
package contract changes; keep both scripts and Terraform validation aligned.
`tests/fixtures/spotto-aws-setup-current.json` is generated from the current API with
Terraform's `tests/fixtures/generate-fixture.ts`; it also proves setup without legacy
AWS-managed policy attachments. Retain the legacy fixture for backward compatibility.
